# Membership Card Protocol — Capability Status (Factual Floor)

**Purpose:** honest, code-grounded status of the five near-term capabilities, for marketing claims to build on. Sourced from `plans/spec-consistency/inconsistencies/code-*.md` (Phase 3 spec-vs-code audit, dated 2026-07-16/17), `integration_tests/reports/2026-07-23-full-coverage.md` (204 passed / 52 todo across 23 suites), and `plans/completed/milestones/*`. Where evidence conflicts or is thin, status is deliberately marked "partial" rather than "built."

| # | Capability / Component | Status | Evidence | Confidence |
|---|---|---|---|---|
| 1 | **Create & distribute membership cards** — Press issuance, IPFS storage, on-chain registration | **Partial** | Press has 107+ passing tests, all 23 P-xx error codes covered (`press-phase-4-summary.md`); `open_offer_creation`/`card_signing`/`card_offering_and_acceptance` integration suites fully green. But: `appendLogEntry` (card update/history log) has NOT adopted the current spec's `card_state`/`history` design — `version` is hardcoded to `1` with a code comment "placeholder for Phase 3" (`code-card.md`, `code-press.md` Finding 2). Press uses Filebase for IPFS pinning, not the Piñata the spec still names — a real, unresolved architecture divergence. Sub-card deregistration only supports the master-key signer path, not the spec's three-signer model. | High — multiple independent audits and live test runs converge on the same gap (log/versioning incomplete). |
| 2 | **Build apps that verify cards** — verifier SDK, chain walk, revocation, policy checks | **Partial** | Core signature/chain/revocation verification exists in both TS and Python verifier packages and is exercised by `conformance/card_verifier.spec.ts`. But: the "ancestry-chain gap" blocks full chain-of-trust walks in test cards across most of the suite (`card_validation`, `card_updates`, `open_offer_acceptance_*`); `RpcProvider.getLogEntries()` in the verifier implements an old on-chain-enumerable model that doesn't match the current IPFS log-chain design (`code-card.md` Finding 2b, flagged ESCALATE); Phase 2 spec amendments (`capabilities`/`valid_until`/`attestation_level`/`chain_card_addresses`) are **not implemented at all** in either language port (`code-verifier-sdk.md`). Contract-level write-integrity gap (Finding 1 in `code-contracts.md`: signed payload not cross-checked against calldata) undermines the trust the verifier relies on. | High — this is the most heavily audited component; gaps are specific and well-documented, not speculative. |
| 3 | **Message cards / message people via cards** — messaging endpoint, relay, oblivious transport | **Partial, built-and-tested core with an unverified security gate** | `message_routing.md` and `notification_relay.md` suites fully pass; the OHTTP relay endpoint (`POST /ohttp/:target_id`) is fully implemented and matches spec closely (`code-relay.md`). App SDK's inbound message handler, however, only checks raw signature validity and **discards chain/revocation/policy verification results** before accepting a message — a security-relevant gap explicitly flagged "ESCALATE TO DAVID" in `code-app-sdk.md` Finding 3. `client-sdk` (not `app-sdk`/`wallet-sdk`) is the actual home of Matrix message signing/verification, and it's a second, independently-maintained copy of crypto code with no shared CI check against `app-sdk`'s copy. | Medium-high — functional messaging path exists and is tested, but the inbound-verification gap means "message a card" cannot currently be marketed as fully policy/revocation-safe. |
| 4 | **Matrix multiparty chats gated by card ownership** | **Partial — join-time gating works; ongoing/continuous enforcement does not** | Room creation, encryption, and join-time deny paths are live-tested against a real Synapse instance (`matrix-phase-6-summary.md`: 9/9 integration tests, real 403s for missing/malformed attestations). But the event-driven revocation watcher (`watcher.py`) — fully built and unit-tested — **is never started by any process** (`code-matrix-synapse.md` Finding 2, ESCALATE): a card revoked after joining a room is never force-parted; the cache never expires. Additionally, the spec's documented callback mechanism (`check_event_for_spam`) was found factually non-functional for joins in the real Synapse version and replaced in code with an undocumented, "very experimental" callback (`check_event_allowed`) — a spec/code divergence significant enough to be flagged ESCALATE. The satisfying-join happy path (a real card that actually passes a room's policy) has never been exercised end-to-end — blocked by lack of deployed contract/real IPFS pinning in the test environment. | High — two independent security-relevant findings (dead watcher, undocumented join gate) plus an explicit "never exercised with a real satisfying card" gap. This is the least production-ready of the five capabilities. |
| 5 | **Operate infra (press / relay / wallet service)** | **Partial — each service runs and has an operator runbook, but has documented incomplete or divergent pieces** | Press: operator doc (`press/OPERATOR.md`) covers deployment, key rotation, backup; 107+ tests pass. Relay: in very good alignment with spec, OHTTP endpoint implemented and tested, only minor error-string/config-doc divergences found. Wallet service: `wallet-service/docs/matrix-operations.md` exists and full stack boots cleanly in Docker; but sub-card-chain cardholder verification for migration announcements is unimplemented despite being in spec (`code-wallet.md` Finding 1, ESCALATE — auth-boundary gap), and `setupWallet.ts`'s step ordering (backups before device sub-card registration) contradicts the corrected spec (`code-wallet-sdk.md` Finding 1). Full-stack integration run: 204 passed / 52 todo across 23 suites, with 12 of 19 process specs only "partially" covered due to shared environment limits (no deployed contract, single-instance topology, no real DNS/IPFS pinning) — these are environment gaps, not necessarily code gaps, but mean the "run infra yourself" claim hasn't been proven against a production-like multi-instance/federated deployment. | Medium — infra runs and is documented, but no evidence of it having been operated in a real multi-party/production topology; several auth-relevant gaps remain unresolved. |

## Cross-cutting caveats for marketing claims

- **Contract-level write-integrity bug** (`code-contracts.md` Finding 1): the smart contract does not cross-check signed payload contents against calldata on any write operation — described as a potential front-running/write-integrity bypass. This affects the trust model underlying capabilities 1, 2, and 5 and should not be marketed around until resolved or clarified as pre-mainnet.
- **Two parallel client SDK codebases** (`app-sdk`/`wallet-sdk` vs. `client-sdk`) both exist and are both under active development; `client-sdk` — not `app-sdk` — is where actual Matrix messaging crypto lives today. Any "app SDK" claim should be checked against which package is actually meant.
- Multiple findings above are explicitly logged as **"ESCALATE TO DAVID"** in the audit trail and, as of the source documents, appear unresolved. Treat these as open risk, not settled fact, until confirmed otherwise.
- Integration-test coverage (204 passing) is real and substantial, but roughly two-thirds of process-spec suites are only "partially" covered, mostly due to test-environment limits (no deployed contract, no real IPFS pinning, single-service topology) rather than proven end-to-end in a production-equivalent setup.

## TODO — post-quantum messaging claim (opened 2026-08-15, from audience interview)

David wants to advertise the assurance **"messages sent with cards are post-quantum encrypted."** Spec supports it; implementation and precision both need confirming before the claim ships.

**Spec position (confirmed, no change needed):** `ARCHITECTURE.md` ADR-004 normatively pins **ML-KEM-768** (FIPS 203) for E2E message encryption; ADR-007 specifies "ML-KEM + ML-DSA-44"; `messaging_protocol.md` MSG-OQ-3a confirms messages are encrypted to the recipient's static ML-KEM public key carried on their card. Cards therefore already carry an ML-KEM key by design — no architectural change required.

**Wording discipline.** ML-DSA-44 (FIPS 204) is a *signature* algorithm and encrypts nothing. Any copy describing it as an "encryption key" is factually wrong and will discredit the surrounding claims with the security reviewers David intends to invite. Correct split: **ML-DSA-44 signs; ML-KEM-768 encrypts; secp256r1 authorizes on-chain writes and is classical, with a designed migration path (ADR-012).**

**TODO-1 — verify implementation matches spec.** Confirm that card-to-card messaging in `app-sdk` / `client-sdk` actually performs ML-KEM-768 encapsulation, rather than falling back to classical ECDH or relying on Matrix's Curve25519-based Olm/Megolm. Note `client-sdk`, not `app-sdk`, currently hosts Matrix messaging crypto. **Owner: security advisor bench** — this is a good, specific recruiting question.

**TODO-2 — forward secrecy caveat.** MSG-OQ-3a: messages are encrypted to a *static* ML-KEM key, so compromise of that key allows retroactive decryption of any captured ciphertext. The spec reasons this is P2 because wallet services do not retain ciphertext at rest, which is sound. But the brand explicitly aims to resemble **Signal**, whose signature property is forward secrecy via one-time prekeys — so this gap will be probed early by anyone taking the comparison seriously. The assurance must not imply forward secrecy until prekeys exist.

**Interim status label:** post-quantum message encryption is **specified and designed, pending implementation verification** — not "built."

## Open items behind the assurance register (opened 2026-08-16)

`branding/assurances.md` is written to be publishable and deliberately carries no internal caveats. The claims it makes are design guarantees to be tested against; these are the tests still owed. Each maps to a numbered assurance.

| 2 | Determine what a **wallet service** can infer about the set of cards a holder keeps. A4 and A8 both assert it can infer nothing; the keyring blob is replicated across the federation per ADR-009-AMEND, so the claim needs testing rather than assuming. | A4, A5, A8 | No — may change wording |
| 3 | Close the revocation gap: `appendLogEntry` has not adopted the spec's `card_state`/`history` design (`version` hardcoded to 1, "placeholder for Phase 3"), and the Matrix revocation watcher is built but never started, so a card revoked after a room join is never force-parted. | A2 | **Yes for pilots** — A2 is the load-bearing claim for the accountability story |
| 4 | Confirm the press write-integrity finding (contract does not cross-check signed payload against calldata) does not undermine A2's claim that an invalid card is caught at first verification. | A2, A8 | No — verify before security review |
| 5 | Decide whether and where to publish the results of assurance testing. The method's honesty depends on unflattering results being published too. | Method | No |

**The wallet service is the component a sharp reviewer will focus on.** It holds the encrypted keyring (A5), operates the card inbox (A6), and is asserted to be unable to correlate cards (A4, A8). Items 1 and 2 both land on it. Worth commissioning a focused review of the wallet service's inference surface as a single piece of work.
