## 2. No Application Service wired into this stack's Synapse

**Spec:** all of Wave 2 — every Matrix suite needs a real Matrix account
for a card.
**Components:** `integration_tests/env/synapse/homeserver.yaml.template`,
`wallet-service/src/matrix/{provisioning,token-minting,appservice-tokens}.ts`.
**Observed:** `wallet-service`'s `POST /matrix/token`/`POST /matrix/rooms`
(the "normal" way a client provisions a shadow Matrix account and creates
a card-gated room) fail before ever reaching Synapse — `readAppServiceAsToken()`
reads a file (`wallet-service/matrix/secrets/appservice-as-token.txt`)
that doesn't exist in this stack's `wallet-service` image, and this
stack's Synapse has no `app_service_config_files` entry to accept an AS
login even if a token were supplied. The `homeserver.yaml.template`'s own
header comment already documents this as a known, deferred TODO — not a
surprise found this session.
**Expected:** An Application Service registered for wallet-service's
shadow-account bridge, matching `wallet-service/docker-compose.yml`'s own
(separate) stack, which does have this wired.
**Suspected cause:** Genuinely just not done yet — Task 1.7 ("wallet-service
under workerd") brought wallet-service into this compose stack but never
closed this specific loop.
**Workaround used, not a fix:** every Wave-2 suite bypasses wallet-service's
provisioning entirely (`suites/support/matrixAdmin.ts`) — registering test
Matrix users directly via Synapse's admin shared-secret API at the exact
`@card_<hex>:server` localpart a real shadow account would have.
`deriveMatrixUserId`/`verifyMatrixUserIdBinding` are pure functions of a
card's keypair, so this is a full substitute for everything the *policy
module* cares about — but it means nothing in Wave 2 exercises
wallet-service's own AS-integration code at all, and `room_discovery.spec.ts`'s
room index stays permanently empty in this environment (§1's
`POST /matrix/rooms` write path is unreachable), since the bypass creates
rooms directly on Synapse, never touching wallet-service's Postgres.
**Triage: defer.** Real, bounded, has a working reference implementation
to copy from (`wallet-service/docker-compose.yml`'s own AS wiring) — but
non-trivial (secrets generation/mounting, `app_service_config_files`,
confirming `wallet-service`'s file-based token-reading approach even
survives its `cloudflare-module`/workerd build target, which is genuinely
uncertain and untested). Worth scoping as its own task rather than folding
into Wave 3.

## 3. Chain-walk path crashes under Synapse's Twisted reactor — FIXED 2026-07-21

**Status: resolved**, same day as the checkpoint.
**Spec:** `matrix_join_attestation_and_revocation.md §3.3`'s "Predicate
evaluation itself throws... Deny... This is the module's last line of
defense — a bug in the evaluator must not become an accidental allow."
**Components:** `matrix_policy_module/attestation.py`'s
`verify_join_attestation` → `chain_context.py`'s
`walk_join_attestation_chain` → `membership_card_verifier`'s
`CardVerifier.verify_envelope` (Python package, `card_verifier.py`).
**Observed:** A validly-signed, correctly-bound join attestation for a
card that was never minted anywhere (no chain to walk) reached real
chain-walk code and crashed with `RuntimeError: await wasn't used with
future` inside `card_verifier.py`'s `asyncio.gather(...)` call. The
exception was not caught; it propagated to Synapse's HTTP layer as a raw
`500`, not the `403 M_FORBIDDEN` every other deny path produces.
**Root cause, confirmed**: this Python package runs embedded inside
Synapse's `matrix_policy_module`, whose coroutines are driven by Twisted's
reactor via `Deferred.fromCoroutine` — not a bare asyncio event loop.
`asyncio.gather(...)` wraps each awaitable in a genuine `asyncio.Task` via
`ensure_future()`; Twisted's coroutine-driving machinery does not reliably
recognize the resulting `gather()` awaitable as it steps the generator,
producing exactly this `RuntimeError`. A plain sequential `await` per
iteration is the supported case Twisted's generator-driving code handles
correctly — no `asyncio.Task`/`ensure_future` wrapping involved.
**Fix**: replaced every `asyncio.gather(...)` call in the Python
verification path with sequential awaits, preserving order (which callers
already relied on) — four call sites total: `card_verifier.py`'s
`verify_envelope` (the one actually hit by this suite),
`stages/stage4.py`'s per-chain-member CardEntry/event-log fetch (would
have hit the identical crash the moment any test exercised a real,
multi-link chain — not yet reached by any suite before this fix),
`stages/stage6.py`'s EAS-annotation fetch (same, not yet reached),
`matrix_policy_module/rpc_provider.py`'s `get_card_event_log` (same,
fixed pre-emptively since it's the exact same pattern one level lower).
Removed the resulting unused `import asyncio` from all four files.
**Verification**: `verifier-py`'s own pytest suite (140 tests) and
`matrix-policy-module`'s own pytest suite (98 tests) both green after the
change; rebuilt the `synapse`/`synapse-init` Docker images and re-ran
`matrix_room_membership.spec.ts` against the live stack — the previously-500ing
scenario now correctly returns `403 M_FORBIDDEN`. Full suite (12 files,
110 tests) confirmed green twice consecutively afterward.
**Triage: fix-now — done.** This was the first attestation in the whole
Wave 1+2 suite set to actually reach real chain-walk code, so the same
crash would very likely have resurfaced (in each of the three other call
sites) the moment any future suite exercised a multi-link chain or EAS
annotations — fixing all four now, rather than only the one this suite
happened to hit, avoids re-discovering the same root cause three more
times across Wave 3/4.

## 4. Room creator's own first post is denied — FIXED 2026-07-23

**Status: resolved.**
**Spec:** `matrix_join_attestation_and_revocation.md §2`'s "Creator
auto-join, carried over unchanged" — states plainly that the creator's
membership "must still be entered into the membership registry... or
their first post would have no registry entry to resolve against."
**Components:** `matrix_policy_module/module.py` (fix location — see
below, not `room-creation.ts` as originally guessed).
**Observed:** Confirmed via a throwaway probe script before writing the
formal test, then encoded as a real regression assertion
(`matrix_join_attestation_and_revocation.spec.ts`): a room creator's very
first `PUT .../send/m.room.message/...` to their own freshly-created room
was denied `403 M_FORBIDDEN`, because nothing in the room-creation flow
recorded `(room_id, creatorMatrixUserId) → card_hash` in the membership
registry.
**Original suspected cause (revised after investigation):** this report
originally guessed the fix was "localized to `room-creation.ts`," on the
assumption that `check_event_allowed` never fires for the creator's own
join during room creation (matching the spec's language about
`check_event_for_spam`/`user_may_join_room`). **A live debug probe proved
this wrong**: `check_event_allowed` genuinely *does* fire for the
creator's auto-join — the spec's claim was written about a different pair
of callbacks and never re-verified after `check_event_allowed` later
became the real production join gate. The actual reason nothing
registered: at the point the creator's join event is checked,
`m.card.policy` isn't in `state_events` yet (it's a *later* `initial_state`
entry in the same `/createRoom` request), so the module's "not a
card-gated room yet" early-return fires before any registration logic
runs.
**Also revised**: `wallet-service` cannot build the fix itself —
`createMatrixRoomViaSynapse` never holds a card's signing key
(wallet-service is deliberately non-custodial), so it cannot sign a
join-attestation-shaped proof of the creator's own `card_hash` no matter
where in its flow such a call was added.
**Fix**: a new custom state-event type,
`io.cardprotocol.room_creator_attestation`, that `check_event_allowed`
recognizes and verifies (`module.py`'s new `_register_creator_membership`)
— the creator's client submits it as a follow-up state event once
`room_id` is known (it cannot be part of the `/createRoom` request itself,
since `room_id` doesn't exist until that request returns). Reuses
`client-sdk`'s existing `buildJoinAttestation` unchanged. Unlike an
ordinary join, registration here does not require the creator's card to
satisfy the room's own policy, per the spec's own "trusted by virtue of
having created the room" language. A second bug surfaced while wiring
this up and was fixed in the same pass: `canonicalize()` (deep inside
signature verification) doesn't accept Synapse's `JsonObject`/
`immutabledict` type, which is what a custom event's *top-level* `.content`
arrives as (unlike the existing join-attestation path, which only ever
reads a *nested* value out of `m.room.member`'s content — nested values
are already plain dict/list once JSON-parsed, so that path never hit
this). Fixed with a one-level `dict(...)` unwrap before verification.
**Verified**: `matrix-policy-module`'s own pytest suite (98 tests) stayed
green; rebuilt the `synapse`/`synapse-init` images and re-ran the live
suite twice — confirmed via `docker compose logs synapse` that the
creator's post-deny reason changes from `membership_not_registered` to
`predicate document unreachable` once the attestation is submitted (proof
the registry lookup now succeeds), and confirmed a creator who never
submits the attestation is still denied exactly as before (the fix is
opt-in, not a security bypass). A fully HTTP-observable `200 allow` for
the creator's post is **not** achievable in this environment — posting
still needs a real, satisfiable predicate document, which needs a real
on-chain card issued under a real policy, the same "no real chain data
reachable" gap already blocking every other happy path in this suite set
— marked `it.todo` with the log-based evidence recorded in a comment
rather than asserted as a passing HTTP check.
**Triage: fix-now — done.**
